# Handoff to the Windows integration agent

Use `integration/verified-stack` as the integration base. Do not merge the older
backend/Arduino copies from `Frontend` over it. The integration commit c73c378
combines sim-hardware 957e965, Frontend f17de46, and backend 888b71d.

## Objective and boundaries

Run the same frontend, verified PhysBox simulations, and Gemini explanation flow
on Windows. Preserve working D5 LED / D9 ON / D8 OFF two-button hardware behavior,
nullable missing-resistor measurements, CORS, and the frontend's API contracts.
Use Gemini (not Claude or Gemma). Diagnose errors; do not substitute mock currents
and label them PhysBox. Do not commit actual API keys, .env files, virtualenvs,
node_modules, generated bytecode, or build output. A key is local configuration,
not part of the code commit. Work on a branch based on the integration branch;
return the commit ID and validation results before changing main or deployment.

## 1. Get the code

Use a clean checkout or preserve existing changes before switching branches.

```powershell
git fetch origin
git switch integration/verified-stack
git pull --ff-only origin integration/verified-stack
# Optional separate branch for Windows fixes:
git switch -c windows/integration-validation
```

Run all commands below from the repository root unless specified. Install
Python 3.13 and Node.js 22 LTS or another Vite-compatible Node version. Do not
copy a Mac virtual environment onto Windows. No PowerShell activation is needed:

```powershell
py -3.13 -m venv simulation/.venv
.\simulation\.venv\Scripts\python.exe -m pip install -r backend/requirements.txt
```

Keep the pinned PhysBox/fastmcp dependencies from simulation/requirements.txt;
do not upgrade them or replace the tested HTTP bridge with another MCP transport
just to resolve a startup failure.

## 2. Local Gemini configuration

Create the ignored file `backend/.env` locally with:

```dotenv
SIMULATOR=physbox
GEMINI_API_KEY=replace_locally_with_actual_key
GEMINI_MODEL=gemini-3.5-flash
AI_TIMEOUT_SECONDS=20
```

The model above is the teammate's configured default, not proof it is available
for every project. Verify access with the actual key. If the API rejects it,
choose an accessible Gemini model and record the tested model in the handoff.
Do not silently switch providers. The key must never be placed in a VITE_ variable.

Check that the key file is ignored without displaying it:

```powershell
git check-ignore backend/.env
```

Settings read backend/.env and then root .env; environment variables override
both. Remove stale overrides if they select the wrong model/provider. Restart
FastAPI after configuration changes. GET /api/gemini/status only verifies client
configuration; it does not prove that inference succeeded.

## 3. PhysBox and FastAPI (two terminals)

Terminal A, repository root:

```powershell
.\simulation\.venv\Scripts\physbox-mcp.exe
```

Keep exactly one https://volt.physbox.io/ tab open **on this Windows laptop**.
Allow local network access if the browser asks. The backend's tested adapter
connects to http://localhost:3141/mcp. A Volt tab on the Mac does not connect the
Windows backend. Requests replace the Volt canvas; save other circuit work.

Terminal B, repository root:

```powershell
$env:SIMULATOR = "physbox"
.\simulation\.venv\Scripts\python.exe -m uvicorn app.main:app --app-dir backend --host 127.0.0.1 --port 8000 --workers 1
```

Use one worker and one backend instance. Do not run simulation CLI scripts while
an API analysis is running. No Arduino is needed to test PhysBox or Gemini.

## 4. Test real simulation plus Gemini

Use a third PowerShell terminal:

```powershell
Invoke-RestMethod http://127.0.0.1:8000/health
Invoke-RestMethod http://127.0.0.1:8000/api/gemini/status
$body = @{ voltage=5; resistance=100; led_forward_voltage=2 } | ConvertTo-Json
$result = Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8000/api/analyze -ContentType "application/json" -Body $body
$result | ConvertTo-Json -Depth 10
```

Required checks:

| Input | Expected result (approximate currents) |
|---|---|
| 5 V, 100 ohm, red Vf=2 | danger; 28.02 mA; correction 220 ohm / 13.29 mA |
| 5 V, 220 ohm, red Vf=2 | safe; 13.29 mA |
| 5 V, 220 ohm, green Vf=2.2 | safe; 12.42 mA |
| 5 V, 220 ohm, blue Vf=3 | safe; 8.98 mA |
| 5 V, 0 ohm, red Vf=2 | danger; original current null; corrected current about 13.29 mA |

Every real simulation must say simulated_with=physbox. At least one successful
key-enabled request must return explanation_source=gemini and a nonempty
recommendation discussing the supplied results. explanation_source=rules means
fallback, not successful Gemini inference. Confirm the model does not present
simulated values as physical measurements or invent an unavailable current.

Test missing/bad key and model failure: simulation results should remain available
with rules provenance, not crash or claim an AI response. Mocked tests cover the
failure paths without spending real API quota.

## 5. Backend tests and frontend

In a terminal used for tests, select mock explicitly so tests do not use Volt or
spend AI quota. Leave GEMINI_API_KEY unset for the test process (the tests mock
AI calls and validate provider behavior separately).

```powershell
$env:SIMULATOR = "mock"
$env:GEMINI_API_KEY = ""
.\simulation\.venv\Scripts\python.exe -m pytest backend -q
# These overrides apply only to this terminal; clear them before restarting
# a real server here, so backend/.env can provide the settings again.
Remove-Item Env:SIMULATOR
Remove-Item Env:GEMINI_API_KEY
cd frontend
npm ci
npm run build
```

Baseline: 59 backend tests and a successful frontend build. Keep the committed
package-lock.json; use npm ci rather than replacing dependencies from scratch.

Create ignored `frontend/.env.local`:

```dotenv
VITE_API_URL=http://127.0.0.1:8000
VITE_USE_MOCK=false
```

Run `npm run dev`, open its localhost URL, and verify the UI's unsafe/corrected
flow plus the recommendation panel. The planner is a static UI prototype; RGB
checks are separate channel simulations. Physical RGB control is not enabled
for the verified two-button sketch. Do not report either as a tested AI/hardware
feature. Missing current must display Unavailable, not 0 mA.

## 6. Optional Uno verification on Windows

Only test hardware if the Uno is physically attached to this Windows machine.
The Arduino on the Mac cannot be reached through a local Windows COM port.
Use hardware/two_button_led/two_button_led.ino, with LED D5 through 220 ohm to
LED anode, cathode GND; ON button D9-to-GND; OFF button D8-to-GND. Internal
pullups are enabled. Upload with Serial Monitor and the backend port closed.
Restart the backend with the detected port (COM3 is only an example):

```powershell
$env:ARDUINO_PORT = "COM3"
```

Find ports with GET /api/hardware/ports. Verify:
- POST /api/hardware/led, {"state":"on"} and {"state":"off"}: acknowledged=true.
- GET /api/hardware/state: actual sketch-reported state, pins 5/9/8.
- POST /api/hardware/switch/follow, {}: website ON action; commands LED_ON.
- GET /api/hardware/switch: closed=true when the latch is ON.
- Physical ON/OFF presses update the website; simultaneous physical presses OFF.

Do not replace these routes with the older single switch D2 / LED D8 protocol.
No Arduino means hardware 503 is expected, not a simulation/AI failure.

## 7. Deployment and return handoff

A successful Windows test does not enable AI on the Mac: the actual backend host
needs its own local key configuration. If moving the live backend to Windows,
start its HTTPS tunnel, update Vercel VITE_API_URL to that tunnel, and rebuild the
frontend. Simulation and USB then depend on that Windows host. If keeping the Mac
as the hardware/backend host, pull the verified code there and configure its key
locally before testing Gemini. Never commit a key to transport it between hosts.

Keep Vercel production unchanged until combined tests pass. Commit only intended
source/docs/lockfile changes, review git diff --cached, and push your Windows fix
branch. Report the commit ID, Python/Node versions, actual Gemini model, test/build
results, live simulation cases, whether Gemini returned a real explanation,
and any untested hardware. Do not include key values in logs or screenshots.
